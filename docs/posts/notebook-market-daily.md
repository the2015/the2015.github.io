# 不花一分钱，GitHub Actions 每天给我推笔记本行情

最近想盯笔记本行情：哪个新品发布了、显卡什么时候降价、内存硬盘什么走势。每天手动刷十几个网站不现实，付费行情 API 又不想为此花钱——于是我给自己搭了一个**零成本日报机器人**：GitHub Actions 按每天早上 9:10 的计划自动汇总资讯，推到我的微信上；实际执行时间可能因平台排队延后。

项目开源在这里：[the2015/notebook-market-daily](https://github.com/the2015/notebook-market-daily)，整个仓库就一个 workflow 文件加两个 shell 脚本。

## 整体方案

```text
RSS 数据源 ──► collect.sh ──► out/report.md ──► notify.sh ──► 微信
(IT之家/                          (关键词过滤            (Server酱 /
 TechPowerUp)                      汇总成 Markdown)       企业微信机器人)
```

每天一次定时任务，跑在 GitHub 的免费 runner 上，全程不依赖任何付费 API 或自己的服务器。

## 数据从哪来

| 来源 | 内容 | 方式 |
| --- | --- | --- |
| IT之家 | 国内数码资讯 | RSS |
| TechPowerUp | 海外硬件资讯 | RSS |
| Ars Technica | 备用海外源（前两个挂了才启用） | RSS |
| 京东（可选） | 商品标价 | 非官方价格接口，无 key |

RSS 抓回来之后不是全塞进报告，而是**按关键词过滤**：中文站匹配「轻薄本|游戏本|拯救者|RTX|Ryzen……」，英文站匹配「laptop|SSD|price cut……」，每个源最多取 12 条，保证推到微信上的内容都能一眼扫完。

一个取巧的决定：**不装任何第三方依赖**。抓取和解析全部用 bash + 内嵌的 Python 标准库（`re` + `html`）完成，不碰 pip。runner 上少一步 `pip install`，就少一个依赖挂掉的故障点——定时任务最怕的就是「上周还好好的，这周突然红了」。

## 怎么送到微信

推送走的是两条现成通道，按配置自动降级：

1. **Server酱**（优先）：个人微信通过服务号收消息，配一个 `SCT_KEY` 就行
2. **企业微信群机器人**：一个 webhook 地址，免费建
3. **都没配**：报告原样输出到 Actions 日志——机器人照样跑，只是不推送

密钥全部放在仓库 Secrets 里，代码里不出现任何凭据。这个「没配置也能跑」的降级设计是刻意的：新仓库刚建好、什么都还没配的时候，workflow 本身就应该是绿的。

## 复制项目前先改这个条件

截至 2026-11-14 核对项目工作流时，任务有一条所有者限制：

```yaml
if: github.repository_owner == 'the2015'
```

如果 Fork 到自己的账号后保持原样，`report` job 会跳过。先把条件中的用户名改成自己的 GitHub 用户名，再按下面的顺序上手：

1. 在自己的仓库启用 Actions，检查上述所有者条件。
2. 手动运行一次 `workflow_dispatch`，先查看收集结果和日志；通知渠道可以稍后配置。
3. 在仓库 Secrets 配置 `SCT_KEY` 或 `WEWORK_WEBHOOK`，再次手动运行并检查实际收到的内容。
4. 核对 `schedule`、Actions 是否启用和后续实际运行记录，不能把一次手动成功当作定时触发已经正常。

运行结果和密钥应留在自己的仓库及账号中。平台免费政策、数据源可用性和通知额度以实际使用时的规则为准。

## 零成本是抠出来的

公开仓库的 Actions 用量本来就有免费额度，但真要做到「零成本跑一年」，关键在几个数字上：

| 防护措施 | 值 | 为什么 |
| --- | --- | --- |
| cron 避开整点 | `10 1 * * *`（北京 09:10） | 整点是调度高峰，官方文档说明排队任务可能被直接丢弃 |
| `timeout-minutes` | 5 | 单次运行强制 5 分钟封顶，避免异常时一路烧额度 |
| `retention-days` | 1 | 报告才 2KB 量级，存 1 天够复查，不长期占存储额度 |
| runner 选型 | ubuntu-latest | 使用标准 Linux runner；公开仓库免费适用范围与其他 runner 价格以当前官方政策为准 |
| 权限 | `contents: read` | 最小权限，防止 workflow 内容被篡改后拿到写权限 |

算一下账：单次运行 1 分钟左右，每天一次，每月约 30–90 分钟。就算不按公开仓库的免费政策、按 Free 计划每月 2,000 分钟的额度算，也只占 5% 不到。

## 已知限制

老实交代，这套方案有明确的边界：

- **京东那节是标价**，不等于券后到手价，而且接口非官方，随时可能失效
- **报告是机器汇总的标题清单**，没做事实核实，结论得点原文自己查证
- 报告里**不含官方出货量统计**——IDC/Canalys 的明细是付费数据，没有免费午餐
- 公开仓库**连续 60 天无活动，GitHub 可能自动停用定时 workflow**；需要到 Actions 检查状态并按平台提示重新启用，不能把一次手动运行当作定时触发已经恢复

所以报告末尾固定有一节「口径说明」，把这几条限制写进每天的推送里——机器给的东西，把不确定性讲清楚比显得权威更重要。

## 一点经验

- 定时任务的设计原则是**降级而不是报错**：源挂了写「本次未获取」，通道没配就打日志，让 pipeline 任何情况下都能跑完
- 给免费额度做防护的三个开关（timeout、retention、最小权限）成本为零，但没有它们，一次异常就可能让「零成本」变成「烧爆额度」
- 与其爬动态网页，不如老老实实用 RSS——稳定、轻量、不惹麻烦，关键词过滤已经够用
